# Step 1: Bot battles go 3v3

## Why here

Online battles already have a full 3v3 engine (`resolveTeamRound`,
`buildTeamState` in `lib/battleEngine.ts`, built in the original plan's
step 5) and a reusable team-picking UI (`components/online/TeamPicker.tsx`).
Bot battles (`components/battle/BattleArena.tsx`) were deliberately kept 1v1
back then, using the older single-fighter `resolveRound`/`buildFighterState`
pair, to avoid building team selection twice at once. This step closes that
gap — entirely a UI + bot-generation change, no new battle math. It's
ordered first, before the result dialog, so that dialog only ever has to
describe one battle shape.

## What changes

### Bot generation
- New `rollBotTeam(playerTeamAverageTotal: number): OwnedPokemon[]` in
  `lib/collection.ts` — calls the existing `rollBotOpponent()` three times,
  once per bot, each with an independently random species. No change to
  `rollBotOpponent()` itself or the leveling formula (species' base stats
  scaled by `playerTeamAverageTotal / species.total`, then rolled through
  the same `rollStatAround()` used everywhere else) — this step is "call it
  3 times," not new math.
- `playerTeamAverageTotal` is the average `total` across the 3 Pokémon the
  player picks for that fight (mirrors today's single-Pokémon leveling,
  generalized to a team average instead of one value) — still computed
  fresh per battle, never persisted, same as today.

### Client (`components/battle/BattleArena.tsx`)
- Gains a pre-fight picking screen: reuse `TeamPicker.tsx` as-is for the
  selection UI, but its `onSubmit` callback starts the local battle
  immediately (`rollBotTeam()` + `buildTeamState()` for both sides) instead
  of making a network call — bot battles have no room, no server
  authority, and stay fully client-side exactly as they are today.
- Local battle state changes from `{ f1: FighterState, f2: FighterState }`
  to `{ team1: TeamState, team2: TeamState, awaitingForcedSwitch, ... }`,
  matching `RoomState`'s shape, and round resolution calls
  `resolveTeamRound()` instead of `resolveRound()`.
- `FighterCard` already supports the `team`/`activeIndex`/`onSwitchTo` props
  (built for online 3v3, unused here until now) — wiring them in gives the
  bench/switch UI for free, no new component needed.
- The "Auto Battle" toggle needs to pick a legal action each tick instead of
  always attacking: attack with a random affordable move by default: if the
  active Pokémon has fainted (a forced-switch state), auto-pick the first
  alive bench member instead.
- The bot side needs its own simple decision logic per round (it already
  does for 1v1 — picks a random affordable move, or a free 0-cost move if
  nothing is affordable): extend this so a bot with a fainted active
  auto-switches to its first alive bench member rather than getting stuck.

### Server
No changes. `POST /api/battles/bot-result` still just takes `{ won:
boolean }`, rolls the 25% lootbox chance, and inserts a `match_results` row
— a 3v3 bot fight still produces exactly one win/loss outcome, so this
endpoint's contract doesn't change. (Optional nicety, not required for this
step: since bot fights now have a real 3-member team like online matches
do, `bot-result` could start populating `match_results.team_snapshot` too,
which today only online matches get — worth doing if convenient, not a
blocker.)

## End state

- [x] Starting a bot battle requires picking 3 owned Pokémon first (via the
      reused `TeamPicker`), same as online.
- [x] The bot team is 3 independently rolled Pokémon, random species, each
      leveled to the player's picked team's average total — verify by
      checking rolled bot stats track a deliberately weak vs. strong picked
      team differently.
- [x] Switching — both a voluntary mid-battle switch and a forced switch
      after a faint — works locally exactly as it does in online battles.
- [x] A full 3v3 bot battle can be played to a team wipe on either side,
      manually and via Auto Battle.
- [x] `/api/battles/bot-result` still fires exactly once per completed
      battle with the correct win/loss and (if implemented) a lootbox roll
      only on a win.
- [x] `npm run build` / `npm run lint` clean.

### Validation notes (2026-08-07)

- `npm run build` and `npm run lint` both clean.
- Wrote a temporary standalone simulation (deleted after running) that calls
  the exact same engine functions `BattleArena.tsx` calls —
  `buildTeamState`/`resolveTeamRound`/`rollBotTeam` — and drives 200 full
  local 3v3 battles end-to-end with the component's own decision rules
  (random affordable move, forced switch → first alive bench member). All
  200 terminated correctly with a winner; 710 forced switches were observed
  across those battles, confirming that path is exercised; bot leveling was
  confirmed to scale with `playerTeamAverageTotal` (avg total ≈99 at
  playerLevel=100 vs. ≈595 at playerLevel=600).
- Ran an HTTP-level check against a real local dev server using a disposable
  Supabase test account (created/deleted via the Auth admin API, signed in
  through the app's real `@supabase/ssr` server client so cookies match a
  real browser session): confirmed the account had 3 starters, `GET
  /battle` rendered the 3v3 team-picker with no error boundary, and
  `POST /api/battles/bot-result` still behaves exactly as before — 12 wins
  produced at least one lootbox grant (25% roll), 1 loss produced none, and
  all 13 calls produced exactly one `match_results` row each.
- Not verified (no browser automation tool available in this environment):
  visually clicking through a battle by hand. The manual-click code paths
  (`MoveButton onClick` → `submitAction({ type: "attack", moveIndex })`,
  bench `onSwitchTo` → `submitAction({ type: "switch", teamIndex })`) are
  the same `submitAction` function and same `BattleAction` shapes the
  simulation drove directly — reviewed by hand but not clicked through in a
  real browser.
